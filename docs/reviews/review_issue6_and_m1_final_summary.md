## 1. 总体评价

## 2. 关键风险与整改项

### 🔴 H1：Spectre.Console Live Panel 与捕获线程耦合风险

**风险描述**  
`Spectre.Console` 的 `Live` / `AnsiConsole.Live` 渲染通常运行在 UI/主线程，而 WGC 捕获、编码、采样是高频后台 I/O。如果后台线程直接调用 `Live` 更新面板，或主线程被阻塞等待帧，会导致：

- 控制台渲染撕裂、闪烁或死锁；
- 捕获回调被 UI 更新阻塞，造成丢帧；
- Spectre 的 `LiveRenderable` 并非线程安全，跨线程更新可能抛异常。

**整改建议**  
- 采用 **Channel / BlockingCollection** 将捕获元数据（FPS、已录制时长、采样数）投递到 UI 线程，由 UI 线程统一刷新；
- 或者将 Spectre Live 运行在独立线程，捕获引擎通过不可变状态快照更新；
- 明确 `IHostedService` 的 `StartAsync` / `StopAsync` 与 UI 循环的生命周期关系。

---

### 🔴 H2：F6/F7 全局热键的消息循环与线程公寓模型

**风险描述**  
Windows 全局热键有两种常见实现：

1. `RegisterHotKey` + `GetMessage` 消息循环；
2. `SetWindowsHookEx(WH_KEYBOARD_LL)` 低层键盘钩子。

两者都需要一个**带消息泵的 STA 线程**。如果 CLI 基于 Generic Host 运行在默认 MTA 线程池，且没有消息循环，热键事件可能：

- 完全不触发；
- 在退出时未注销，导致系统级热键残留；
- 与 Spectre 的输入读取冲突。

**整改建议**  
- 使用专用 `Thread` + `Application.Run()` 或自定义 `GetMessage` 循环承载热键；
- 在 `IHostedService.StopAsync` / `AppDomain.ProcessExit` 中**确保注销**；
- 将热键映射抽象为 `IHotKeyService`，支持配置化键位与平台回退。

---

### 🔴 H3：异常退出时 MP4 / 数据集文件完整性

**风险描述**  
WGC + MediaTranscoder / FFmpeg 编码器在进程崩溃、Ctrl+C、窗口句柄失效时，若未正确 flush `moov` atom 或关闭文件流，会导致：

- MP4 无法播放；
- 数据集目录中帧与视频时间戳不一致；
- 临时文件残留。

**整改建议**  
- 使用 `IHostApplicationLifetime.ApplicationStopping` + `Console.CancelKeyPress` 注册**同步/异步联合关闭**；
- 在 `StopAsync` 中按顺序：停止采样 → flush 编码器 → 关闭视频文件 → 释放 WGC session → 写数据集元数据；
- 引入“分段录制”或“moov 前置”策略，降低异常退出损失；
- 对输出文件做最终校验（如检查 MP4 `ftyp`/`moov` box）。

---

### 🔴 H4：WGC / Direct3D 资源生命周期与多线程

**风险描述**  
`Windows.Graphics.Capture` 的 `Direct3D11CaptureFramePool`、`GraphicsCaptureItem`、`GraphicsCaptureSession` 以及 `ID3D11Device` 都有严格的线程亲和性与 COM 公寓要求：

- `FramePool` 通常在创建线程上触发 `FrameArrived`；
- `GraphicsCaptureItem.Closed` 事件必须处理，否则窗口关闭后访问句柄会崩溃；
- Direct3D 设备跨线程使用需 `MTA` 或正确 Marshal；
- 未释放的 `SharpDX` / `Vortice` / `Win2D` 资源会造成显存泄漏。

**整改建议**  
- 明确捕获线程模型：推荐**单一线程**负责 WGC + D3D + 编码，避免线程跳转；
- 订阅 `Closed` 事件并触发捕获重启或优雅退出；
- 使用 `using` / `Dispose` 链，并在退出时调用 `GC.WaitForPendingFinalizers` 二次确认；
- 对 D3D 设备进行 `DeviceRemoved` 检测与恢复。

---

### 🔴 H5：DatasetSampler 单帧采样阻塞捕获流水线

**风险描述**  
如果在 `FrameArrived` 回调中直接进行 JPEG/PNG 编码并写入磁盘，单帧 I/O 耗时（尤其机械硬盘或高分辨率）会阻塞下一帧，导致：

- 帧率抖动；
- 视频与采样帧时间戳漂移；
- 高负载下 WGC 帧池被填满，丢失帧。

**整改建议**  
- 引入**有界生产者-消费者队列**（`Channel<FrameSample>`），采样请求入队，后台线程异步编码落盘；
- 对队列满的情况定义策略：丢弃最旧帧 / 跳过非关键帧 / 反压降低采样率；
- 采样文件名包含**视频时间戳（ms）** 而非仅序号，便于 M2 对齐。

## 5. 进入 M2（视觉与 ROI）的衔接建议

### 5.1 架构层面

- **将捕获引擎拆分为独立服务**：`ICaptureService`、`IRecordingService`、`ISamplingService`、`IHotKeyService`，通过 DI 组合，便于 M2 插入视觉预处理节点；

- **统一时间基准**：所有帧、采样、事件以 `Stopwatch.GetTimestamp()` 或捕获时间戳为唯一 ID，M2 做 ROI 标注时可直接对齐。

- **制定 Dataset Schema v1**：
  ```json
  {
    "session_id": "uuid",
    "video_path": "...",
    "fps": 60,
    "resolution": [1920, 1080],
    "frames": [
      {"index": 0, "timestamp_ms": 0, "file": "frame_00000000.png", "roi": null}

  ```

### 5.3 工程层面

### 5.4 视觉层面（M2 目标）

## 给 M2 的衔接建议（无论 M1 最终结论如何，现在就该做的事）

1. **锁定帧-数据集的时间映射契约**：M2 做 ROI 标注和视觉模型训练，第一件事就是要能把 MP4 中任意一帧精确对应到 DatasetSampler 输出的采样帧（或反过来）。这个映射协议现在必须以文档/接口形式固化下来，否则 M2 一开始就要返工。
