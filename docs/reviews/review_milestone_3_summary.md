## 四、进入 M4 的衔接建议

M4 的核心是“局内状态机 + 超几何概率推演”。M3 作为感知层，建议按以下方式与 M4 解耦：

### 4.1 领域模型层（新增）

在 M3 与 M4 之间引入稳定的 `GameState` 领域模型，避免 M4 直接消费原始检测/OCR 结果：

```text
Raw Perception (M3)
    ↓
Observation { timestamp, source, confidence, rawValue }
    ↓
Perception Fusion / Temporal Filter
    ↓
GameState { board[4][7], bench[9], shop[5], gold, stage, health, ... }
    ↓
M4 State Machine + Probability Engine
```

- `Observation` 必须携带置信度与来源（YOLO class / OCR text / heuristic）。
- 对同一槽位做多帧一致性过滤（例如：连续 3 帧识别为同一单位才写入 `GameState`）。
- 对低置信度观察标记为 `Uncertain`，M4 决策时按最坏/期望情况分别计算。

### 4.2 状态机设计

- 采用 **事件驱动状态机**：`ShopOpened`, `CombatStarted`, `RoundEnded`, `GoldChanged` 等事件由 M3 感知触发。
- 状态转换只依赖 `GameState` 快照，不依赖原始图像，便于单元测试与回放。
- 增加 `InvalidState` 保护：当感知结果与状态机内部假设冲突时（如棋盘出现不可能的单位数），触发重新感知或人工确认。

### 4.3 超几何概率引擎

- 独立为 `HypergeometricProbabilityEngine`，与视觉层完全解耦。
- 输入：牌库剩余数量、当前等级 roll 概率、目标卡数量、已持有/已见卡数量。
- 输出：抽到至少 k 张目标卡的概率、期望抽卡数、三星完成概率。
- 建议先用精确组合数学实现，必要时再用蒙特卡洛做近似；必须有独立单元测试覆盖边界（牌库为空、目标卡已抽完等）。

### 4.4 动作执行与坐标回传

- M4 决策出的动作（买卡、卖卡、移动、刷新、升级）需要屏幕坐标时，统一通过 M3 提供的 `SlotCoordinateProvider` 获取，而不是在 M4 里硬编码坐标。
- 建议定义 `SlotId` 枚举（如 `Board(0,0)`、`Bench(3)`、`Shop(2)`），M4 只操作 `SlotId`，坐标映射由 M3 负责。

### 4.5 可观测性

- 在 M4 开发前建立感知日志：每帧保存原始检测框、OCR 结果、纠错前后文本、最终 `GameState`。
- 这将极大加速 M4 调试“状态机为何做出错误决策”的问题。

## 2. OnnxInferenceEngine（Issue #10）—— 重点审查

### 2.1 生命周期管理
- **必须核实**：`InferenceSession` 是否实现 `IDisposable` 且在服务生命周期结束时被正确释放？DirectML EP 的显存/句柄泄漏在长时间跑局（连续对局采集）场景下是致命的。
- **必须核实**：是否存在**每帧重建 Session** 的反模式？这是最常见的"能跑但性能灾难"的实现方式。

### 2.2 DirectML → CPU 自动降级
- 这个功能描述本身很好，但降级逻辑的**触发条件**和**触发时机**是审查重点：
  - 是在 `SessionOptions` 创建时 try DirectML catch 降级到 CPU EP？还是运行时推理失败才降级？后者会导致**推理中途状态不一致**（部分帧 DirectML 输出、部分帧 CPU 输出，若两者数值精度不同会导致 NMS 阈值行为漂移）。
  - **要求**：降级决策必须在 Session 初始化阶段一次性完成并记录日志（含设备名、驱动版本），不允许运行时动态切换 EP。
- 是否有针对"无 GPU / 驱动过旧"环境的**集成测试**（而非 Mock）？"210 项测试"里如果 DirectML 降级测试是 Mock 掉 `SessionOptions`，则完全没有验证价值，必须有一个在纯 CPU CI runner 上跑通的用例。

### 2.3 零拷贝张量
- "内存张量零拷贝"这个描述需要具体到实现：是用 `OrtValue.CreateTensorValueFromMemory` 直接包装屏幕截图的 `byte[]`/`Span<byte>`，还是仅仅是把 Bitmap 转换后又做了一次隐式复制？
  - **要求**：提供从截图（GDI+/Windows.Graphics.Capture）到 `float[]` NCHW 张量的完整数据路径说明，确认是否存在 `Bitmap.LockBits` → `Marshal.Copy` → `new float[]` 三次拷贝的隐藏成本。这直接决定"零拷贝"是真实优化还是文档夸大。

## 3. YoloDetectorService（Issue #11）—— 重点审查

### 3.1 输出头解码
- YOLOv11n 是 anchor-free、DFL（Distribution Focal Loss）解码结构，与 v5/v8 的解码逻辑**不完全相同**。要求确认：
  - decode 逻辑是否针对 v11 的输出 shape（通常是 `[1, 4+nc, 8400]` 且无 objectness 分支）单独实现，而不是从 v8/v5 代码抄过来但没适配 objectness 分支消失的差异。这是最容易出现"能跑但精度是错的"隐患的地方。
  - 多类别置信度过滤：是 `class_conf` 直接 sigmoid 后阈值过滤，还是有额外的 `obj_conf * class_conf` 乘积？如果误用了 v8 之前的公式，会导致系统性漏检。

### 3.2 NMS 几何计算测试
- "NMS 几何计算"测试要看是否覆盖了：
  - 完全重叠框、零面积框（w=0 或 h=0，浮点误差场景）、跨类别 NMS vs 同类别 NMS 策略（棋盘格子边界的棋子检测容易在格子交界处产生跨类别误检，是否做了 class-agnostic NMS 兜底）。

### 3.3 坐标反向映射（棋盘 4x7 + 备战席 9）
- **这是本模块最大的业务风险点**，且概览完全没提及验证方式：
  - 屏幕分辨率/UI 缩放（125%/150% DPI）变化时，棋盘格子的像素坐标映射表是硬编码还是基于检测到的棋盘边界动态计算（透视/仿射变换）？
  - 如果是硬编码坐标表，**必须要求提供分辨率适配方案**，否则该服务在非默认分辨率下会直接报废，这在实际 M4 状态机接入前是必须暴露的架构缺陷。
  - 要求提供至少 2 种分辨率/DPI 下的映射准确率测试数据。

## 4. PaddleOcrService（Issue #12）—— 重点审查

### 4.1 Levenshtein 模糊纠错
- 需要确认纠错是**在候选词典范围内做最近邻匹配**（正确用法），而不是无脑对任意 OCR 输出做全局字典 Levenshtein 最小值替换（这会把"7金币"错误纠正成词典里形似的卡名，属于过度纠错，业务上比不纠错更危险）。
- 阶段数字（如 "3-2"）识别的容错策略要单独审查：数字识别错误在下游状态机（M4）里是**致命错误**（阶段判断错误会导致概率推演整体错位），不能与卡名文本纠错用同一套模糊容忍阈值。**要求数字字段禁用模糊纠错，仅允许字符级白名单 + 置信度阈值拒绝**。

### 4.2 GameSeasonDictionary
- 是否随赛季更新（新卡池）有版本化机制？如果词典硬编码在代码里，赛季更新后 OCR 纠错会直接失效或误纠错，这是长期可维护性问题，建议纠正为可配置/可热更新资源文件。

## 6. M3 验收结论

**结论：条件性通过（Conditional Pass），不予终验（Not Final Accepted）。**

理由：架构分工（推理引擎 / 检测 / OCR 三层解耦）合理，功能覆盖面符合 Issue 范围，但**当前提交材料的证据链不足以支撑"验收通过"这一结论**——核心风险集中在：
1. DirectML 降级的真实性验证缺失；
2. YOLOv11n 解码公式与坐标反向映射的分辨率健壮性缺乏证据；
3. OCR 数字字段纠错策略存在业务风险且未被概览区分说明；

## 7. 进入 M4（局内状态机与超几何概率推演）的衔接建议

M4 的核心是**基于视觉管线输出的离散状态**做超几何分布概率计算（例如"当前费用池中目标卡剩余数量 / 总剩余数量"的抽卡概率），这意味着：

1. **接口契约先行**：M4 状态机不应直接消费 YOLO/OCR 的原始输出（框坐标、置信度、OCR 字符串），必须先定义一层 **`GameStateSnapshot` DTO**（结构化后的：商店 5 卡槪的卡名+星级、金币数、阶段数、棋盘 28 格占用、备战席 9 格占用），由 M3 三个服务共同产出并做**一致性校验**（例如金币数是数字识别结果，若识别失败应返回 `Nullable<int>` 而非默认 0，防止 M4 概率计算静默使用错误金币数触发错误策略建议）。

2. **置信度传递，不要在 M3 层"吃掉"不确定性**：YOLO 检测置信度、OCR 识别置信度应作为字段传递到 `GameStateSnapshot`，M4 的超几何概率模型在低置信度输入下应能够**降级为"不给出确定性建议，仅给出区间估计"**，而不是假设视觉输入 100% 正确。这是当前概览完全没有涉及、但对 M4 正确性至关重要的一环。

3. **卡池计数的数据源可靠性是 M4 概率模型的地基**：超几何推演依赖"某费用某卡已被抽取/上场的总数"这一状态，该状态**跨帧累积**，任何一帧 OCR/YOLO 的误检误识都会污染累积计数并在多轮抽卡后放大误差。建议 M4 设计增加"异常帧丢弃/回滚"机制（例如同一格子连续 3 帧检测结果不一致时，采用多数投票而非最新帧覆盖），这个纠错逻辑应该在 M3→M4 的边界层实现，而不是留到 M4 状态机内部零散处理。

4. 建议 M4 启动前先补一个**契约测试（Contract Test）**：固定一批录制好的真实截图序列，跑通"截图→M3 三服务→GameStateSnapshot→M4 状态机初始状态"的端到端管线，作为 M3/M4 交接的验收基线，而不是仅凭单元测试通过就直接切换团队。
