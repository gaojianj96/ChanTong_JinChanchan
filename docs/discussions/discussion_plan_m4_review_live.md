## 1. 超几何分布：结合同行卡池扣减与商店多卡槽联合概率计算的数学严谨性

### ✅ 核心正确性
超几何分布（Hypergeometric Distribution）天然适用于**不放回抽样**场景，与自走棋卡池机制完全吻合：
- 总卡池大小 \(N\) = 所有玩家已购买 + 商店中 + 剩余牌库中的该费用棋子总数。
- 成功数 \(K\) = 当前牌库中特定棋子的剩余数量（需扣减所有玩家已持有、已锁定、已移除的该棋子）。
- 抽样数 \(n\) = 商店刷出的卡槽数（通常为5）。
- 单卡槽出现特定棋子的概率 = \(\frac{K}{N}\)，但多卡槽联合概率需考虑**不放回**。

### ⚠️ 潜在数学陷阱

#### (a) 多卡槽联合概率 ≠ 独立二项式
许多实现错误地将每个卡槽视为独立伯努利试验（即用二项分布），但实际商店刷新是**无放回**的（同一张卡不会出现在两个卡槽中）。超几何分布正确计算了“在 n 个卡槽中恰好出现 k 张特定棋子”的概率：
\[
P(X=k) = \frac{\binom{K}{k} \binom{N-K}{n-k}}{\binom{N}{n}}
\]
但若需要计算**至少出现一张**（即抽到概率），应使用 \(1 - P(X=0)\)。

#### (b) 同行卡池扣减的实时性
- 每个对手的持有情况必须**精确到当前回合**，且需区分“已上场”与“待售区”（通常都计入卡池消耗）。
- 若对手的棋子被合成（3星），则消耗数量为3（或2，取决于合成规则），需正确扣减。
- 若对手卖掉棋子，需**立即归还**到牌库，但归还时机可能影响本回合概率计算（通常卖棋子在回合内生效，但商店刷新在回合开始时已固定）。**建议**：在每次商店刷新前，统一快照所有玩家的持有状态，并以此计算概率。

#### (c) 多费用混合卡池的联合概率
实际商店刷新是按费用分层（1费、2费…）独立进行的，每个卡槽先随机决定费用（根据等级概率表），再从对应费用卡池中按超几何抽取。因此**整体概率是条件概率的乘积**：
\[
P(\text{出现特定棋子}) = \sum_{\text{费用}} P(\text{该费用被选中}) \times P(\text{从该费用卡池中抽到该棋子})
\]
其中 \(P(\text{从该费用卡池中抽到该棋子})\) 必须使用超几何，且需考虑该费用卡池的总大小和剩余数量。

#### (d) 卡池总量动态变化
- 每个费用的总卡池大小是固定的（如1费棋子每种30张，共13种，则总390张），但需减去所有玩家已持有的该费用棋子总数。
- 若使用“全局剩余”而非“个人视角”，则需同步所有玩家的持有数据——这正是第2点要解决的问题。

### ✅ 建议验证方法
- 编写单元测试：固定卡池状态，手动计算超几何概率，与代码输出对比。
- 模拟大量商店刷新（如100万次），统计特定棋子的出现频率，与理论概率做卡方检验。
- 边界测试：当 \(K=0\) 或 \(K=N\) 时，概率应为0或1；当 \(n > N\) 时需截断（实际不会发生，但应防御）。

## 2. 7 名对手侦察快照：多线程并发读写下的不可变安全与时序更新机制

### ✅ 核心设计目标
- 每个对手的“侦察快照”应包含：等级、棋子阵容（含星级）、装备、金币、连胜/连败状态等。
- 快照用于决策引擎（如判断对手强度、克制关系），因此必须**一致且无中间状态**。

### ⚠️ 并发安全风险

#### (a) 写者-读者问题
- 主线程（游戏循环）在每回合开始时更新所有对手的快照。
- 决策引擎（可能运行在独立线程或协程）同时读取快照。
- 若使用可变对象（如 `List<Unit>`），读取线程可能看到部分更新的脏数据（例如棋子列表已更新但等级未更新）。

#### (b) 不可变快照方案（推荐）
- 每回合生成一个**完整的不可变快照对象**（如 `record OpponentSnapshot(...)` 或 `@Immutable` 类），所有字段均为 final。
- 主线程构造新快照后，通过 `AtomicReference<OpponentSnapshot>` 原子替换。
- 读取线程只需 `get()` 一次，即可获得一个始终一致的快照（即使后续被替换，旧快照仍有效）。

#### (c) 时序更新机制
- **更新时机**：应在商店刷新、战斗结算、玩家操作（买/卖/合成）**之后**，但在决策引擎开始计算**之前**。
- **全量 vs 增量**：全量快照更安全（避免增量合并的竞态），但需注意性能（7个对手，每个约几十个字段，全量拷贝开销可忽略）。
- **快照版本号**：可附加一个单调递增的版本号，用于决策引擎判断快照是否过时（可选）。

#### (d) 多线程环境下的额外注意
- 若决策引擎需要访问**多个对手**的快照，应一次性获取所有快照的引用（例如 `List<AtomicReference<OpponentSnapshot>>`），并确保在读取期间这些引用不会被回收（Java/C# 中 GC 安全，C++ 需智能指针）。
- 避免在决策引擎中持有快照后长时间计算，导致快照与最新状态偏差过大——但这是业务问题，非并发问题。

### ✅ 建议实现模式（伪代码）
```java
// 主线程每回合更新
public void onRoundStart() {
    for (int i = 0; i < 7; i++) {
        OpponentSnapshot snapshot = buildSnapshot(opponents[i]);
        snapshotRefs[i].set(snapshot); // AtomicReference
    }
}

// 决策线程读取
OpponentSnapshot snap = snapshotRefs[i].get();
// 使用 snap 进行决策，snap 保证一致
```

### ✅ 验证方法
- 压力测试：启动多个读取线程持续读取，同时主线程高频更新，检查是否出现 `NullPointerException` 或字段不一致。
- 使用 Java `jcstress` 或 C++ `std::atomic` 的 memory_order 验证。

## 3. 战术建议（利息/升人口/装备合成）的规则决策鲁棒性

### ✅ 规则决策本质
战术建议通常基于**确定性规则**（如：金币 > 50 时存利息，否则升人口）或**启发式评分**（如装备合成优先级）。鲁棒性要求：
- 输入异常（如金币为负、人口已满）时不崩溃。
- 规则之间无冲突（如同时建议“存利息”和“花光金币升人口”）。
- 边界条件处理（如 0 金币时利息为 0，升人口所需金币不足时降级建议）。

### ⚠️ 潜在鲁棒性问题

#### (a) 利息计算
- 利息 = floor(金币 / 10)，但上限通常为 5（或 7，取决于版本）。
- 需考虑**本回合战斗胜利/失败后的金币变化**：决策引擎应在战斗结算后、商店刷新前运行，此时金币已包含利息和基础收入。
- 若玩家已负债（金币为负？通常不允许，但防御性检查应返回 0 利息）。

#### (b) 升人口决策
- 当前人口上限受等级限制（如 10 级满）。
- 升人口所需金币 = 当前等级 * 4（常见公式），需检查是否足够。
- 若已满级，应返回“无法升人口”而非报错。
- 与存利息的优先级：通常建议“如果升人口后金币仍 ≥ 50，则升人口；否则存利息”。但需考虑连胜/连败加成，可引入权重。

#### (c) 装备合成
- 装备合成规则通常为：两个相同小件合成一个大件，或特定组合。
- 鲁棒性要求：
  - 输入装备列表可能包含重复、无效装备、已合成装备。
  - 合成建议应输出**可执行的具体步骤**（如“将反曲弓+锁子甲合成幻影之舞”），而非模糊提示。
  - 需检查背包是否有足够格子（若已满，应提示先出售）。
  - 避免循环建议（如建议合成A，但A又需要B，而B尚未获得）。

#### (d) 规则冲突与优先级
- 常见冲突：存利息 vs 升人口 vs 刷牌。应设计**优先级排序**（例如：保连胜 > 存利息 > 升人口 > 刷牌），或使用**效用函数**量化。
- 若多个建议同时触发，应输出**最优先的一条**或**排序列表**，避免矛盾。

### ✅ 建议增强鲁棒性的措施
- 所有规则函数采用 **Result 模式**（返回成功/失败+原因），而非抛出异常。
- 输入参数进行**前置条件校验**（如金币≥0，人口≤max，装备列表非空但允许空）。
- 使用**决策树或有限状态机**显式定义规则优先级，避免 if-else 嵌套混乱。
- 对装备合成，预先计算所有可能的合成配方，并采用**贪心匹配**（优先合成高价值装备）。

### ✅ 验证方法
- 编写**边界值测试**：金币=0, 1, 9, 10, 49, 50, 51；人口=1, 10；装备列表为空、满背包、重复装备。
- 编写**压力测试**：随机生成大量合法/非法输入，确保无崩溃。
- 编写**回归测试**：固定场景下，输出应与人工专家判断一致。

## 一、超几何分布引擎的数学严谨性

### 1.1 总体认可

将"扣减后的剩余卡池 → 商店 5 槽抽样"建模为超几何分布是正确的方向。TFT 的核心机制是**无放回抽样**（每个英雄在共享池中数量上限固定），超几何是天然适配的工具。

### 1.2 需要澄清的关键假设

**问题 A：商店刷新是"批量抽样"还是"序贯抽样"？**

- **批量模型**：5 个槽位是一次性从剩余池中抽出的多元超几何分布（Multivariate Hypergeometric）。此时 5 槽之间**不独立**，联合概率必须用多项式系数计算：

$$
P(X_1=x_1, \ldots, X_k=x_k) = \frac{\prod_{i=1}^{k}\binom{N_i}{x_i}}{\binom{N}{n}}
$$

其中 $N = \sum N_i$ 为剩余池总量，$n=5$ 为商店容量。

- **序贯模型**：每槽独立从前序扣减后的池中抽样，槽位之间条件独立：

$$
P = \prod_{j=1}^{5} \frac{N_{c_j}^{(j-1)}}{N^{(j-1)}}
$$

**Plan 中必须明确选择哪种模型**。我倾向于**序贯模型**，因为 Riot 的实际实现更接近"每帧从池中随机抽一张放入槽位"，且序贯模型在工程上更易增量更新（只需维护剩余池向量）。

**问题 B：等级-费用概率矩阵的耦合**

不同等级下，1/2/3/4/5 费英雄的出现概率不同（如 7 级时 1 费概率显著下降）。Plan 中是否将这个**等级条件概率**作为超几何分布的先验？如果是，需要写成：

$$
P(\text{商店} \mid \text{等级}=L) = \sum_{c=1}^{5} p_c(L) \cdot P(\text{超几何} \mid \text{费用}=c)
$$

否则会出现"用 5 级概率算 7 级商店"的系统性偏差。

**问题 C：联合概率计算的数值稳定性**

当计算"5 槽中至少出现 2 张目标卡 X"时，建议使用**对数空间累加**或**互补事件**：

$$
P(X \geq 2) = 1 - P(X=0) - P(X=1)
$$

直接用浮点阶乘相乘在 $N$ 较大时（特别是 5 费池 $N_5=10$ 但全局池 $N \approx 60$）容易下溢。

### 1.3 扣减源的完整性

需要明确列出所有扣减源，避免漏算：

| 扣减源 | 时机 | 备注 |
|--------|------|------|
| 我方棋盘 + 备战席 | 持续 | 需区分"已锁定"与"可出售" |
| 7 名对手棋盘 + 备战席 | 侦察快照 | 见第二节 |
| 已消耗（被对手购买） | 持续 | 需从对手快照推断 |
| 选秀（Carousel）回合 | 离散事件 | 整局仅若干次 |
| 强化（Augment）转化 | 离散事件 | 部分强化会改变池 |

**建议**：维护一个 `CardPoolLedger` 单例，所有扣减操作走同一接口，避免分散扣减导致池状态不一致。

### 1.4 小结

数学框架方向正确，但**必须在 Plan 中显式声明**：
1. 序贯 vs 批量模型的选择；
2. 等级条件概率的耦合方式；
3. 数值稳定性策略（对数空间 / 互补事件）；
4. 扣减源的完整列表与统一接口。

## 二、7 名对手侦察快照的并发安全

### 2.1 总体架构认可

"快照（Snapshot）+ 不可变（Immutable）+ 时序更新"是处理高频侦察数据的标准做法，方向正确。

### 2.2 关键风险点

**风险 1：快照的"不可变性"边界**

如果快照是 `struct ScoutSnapshot { ... }` 的值类型（C++/Rust）或 `record`（Java 16+），则天然不可变，**读写无需加锁**。但如果内部包含可变容器（如 `List<Trait>`），则需要：

- **深拷贝（Deep Copy）**：每次更新生成全新对象，旧对象继续被读者持有；
- **写时复制（Copy-on-Write）**：仅在修改时复制，降低常态开销。

**建议**：在 Plan 中明确快照的**所有权语义**——是"每次刷新生成新快照，旧快照冻结"还是"原地更新 + 版本号"。

**风险 2：时序一致性（Temporal Consistency）**

侦察数据存在**陈旧窗口**：

```
T0: 线程 A 读取对手 3 的快照（HP=85, 阵容=Z）
T1: 对手 3 实际卖出 1 个 Z，换上 1 个 Y
T2: 线程 A 基于陈旧快照做决策
```

需要：
- **版本号 / 时间戳**：每个快照带 `version: u64` 或 `captured_at: Instant`，决策时检查新鲜度；
- **陈旧阈值**：超过 N 秒或 M 个游戏 tick 的快照应标记为 `Stale`，决策引擎降级使用或触发重新侦察。

**风险 3：并发更新策略**

7 个对手的快照可能被多个线程并发更新（每个对手一个侦察线程，或一个轮询线程串行更新）。两种模式：

| 模式 | 优点 | 缺点 |
|------|------|------|
| 每对手独立线程 | 延迟低 | 锁粒度细，但 7 个原子操作开销不小 |
| 单线程轮询 + 无锁队列 | 实现简单 | 轮询周期决定最大陈旧度 |

**推荐**：单线程轮询 + `AtomicPtr<ScoutSnapshot>` 无锁发布（Linux `__atomic_store_n` / Java `AtomicReference`）。读者通过 `load(acquire)` 获取指针，写者通过 `store(release)` 发布新快照，**全程无锁**。

**风险 4：ABA 问题**

如果使用版本号 + 指针方案，需要确保版本号单调递增（即使指针被回收重用，版本号不同也能区分）。建议 64 位版本号，高位存逻辑时钟，低位存单调计数器。

### 2.3 内存模型建议

如果项目使用 Rust：
- 快照用 `Arc<ScoutSnapshot>` 共享；
- 更新通过 `Arc::swap` 或 `atomic::store` 发布；
- 读者持有 `Arc` 克隆，生命周期独立。

如果使用 C++：
- 快照用 `std::shared_ptr<const ScoutSnapshot>`；
- 容器用 `std::atomic<std::shared_ptr>`（C++20）；
- 或手写 `std::atomic<ScoutSnapshot*>` + 引用计数。

如果使用 Java：
- 快照用 `record ScoutSnapshot(...)`（Java 16+ 不可变 record）；
- 发布用 `AtomicReference<ScoutSnapshot>`。

### 2.4 小结

并发模型方向正确，但 Plan 需补充：
1. 快照所有权语义（深拷贝 vs CoW）；
2. 版本号/时间戳机制与陈旧阈值；
3. 无锁发布的具体原语（按语言选型）；
4. ABA 防护策略。

## 三、战术建议规则的鲁棒性

### 3.1 状态机完备性

Plan 中提到"局内全状态机"，需要确认状态空间是否覆盖：

- **经济状态**：金币区间（<10, 10-19, 20-29, 30-49, 50+）× 利息档位；
- **血量状态**：安全（>70）、警戒（50-70）、危险（30-50）、濒死（<30）；
- **连胜/连败状态**：连胜 ≥2、连败 ≥2、中性；
- **阵容状态**：成型期、过渡期、待替换、已成型；
- **装备状态**：散件持有、合成路径、关键装备缺口。

**笛卡尔积**可能产生数十种复合状态，Plan 中是否定义了**状态优先级**与**冲突解决规则**？

### 3.2 规则鲁棒性的具体担忧

**担忧 1：硬编码阈值的脆弱性**

例如"金币 ≥ 50 立即升人口"。但在以下场景可能反直觉：
- 7 级时 50 金升级到 8 级，但 8 级刷新商店可能找不到关键 4 费卡；
- 此时**保留 50 金吃利息 + 等待下一轮选秀**可能更优。

**建议**：阈值应作为**默认参数**，允许根据阵容类型（速 8 / 速 9 / 赌狗）动态调整。

**担忧 2：装备合成的优先级冲突**

TFT 中装备合成有"对内最优"与"对外最优"的张力：
- 给自己核心 C 位合成 → 提升战力；
- 合成"通用装备"（如守护天使）→ 便于后续轮换；
- 故意不合成 → 保留灵活性。

Plan 中是否定义了**装备合成决策树**？建议至少覆盖：
- 当前 C 位是否已 3 星？
- 是否有更强的 C 位待上场？
- 装备是否会被对手的关键英雄克制？

**担忧 3：升人口 vs 吃利息 vs 刷新的三元决策**

这是 TFT 最核心的决策三角。建议 Plan 中给出**决策矩阵**：

| 血量 | 金币 | 连胜/连败 | 推荐动作 |
|------|------|-----------|----------|
| >70 | <50 | 任意 | 吃利息，等关键回合 |
| 50-70 | ≥50 | 连胜中 | 升人口保连胜 |
| 30-50 | ≥30 | 连败中 | 刷新找牌止血 |
| <30 | 任意 | 任意 | All-in 刷新 |

但这只是骨架，**真实决策需要结合阵容羁绊、对手强度、关键卡费用**。

### 3.3 规则 vs 学习的边界

如果项目最终目标是规则引擎（不引入 ML），则需要接受**规则无法覆盖所有边角情况**的事实。建议：

- **规则覆盖 80% 常见场景**；
- **剩余 20% 异常场景**通过"安全降级"处理（如"无法决策时执行最保守动作：吃利息"）；
- **保留遥测接口**，记录所有决策与结果，便于后续用 ML 替换或增强规则。

### 3.4 小结

战术规则需要：
1. 完整的状态空间定义与优先级；
2. 参数化的阈值（而非硬编码）；
3. 装备合成的决策树；
4. 升人口/利息/刷新的三元决策矩阵；
5. 异常场景的安全降级策略。

## 四、跨议题的协同建议

三个议题并非完全独立，存在耦合：

1. **超几何引擎的输出**（"刷新后看到目标卡的概率"）应作为**战术决策的输入特征**之一，例如"刷新找到关键卡的概率 < 30% 时，优先吃利息而非刷新"；
2. **对手快照**应同时驱动**超几何引擎的扣减**（对手已持有的卡从池中扣除）与**战术决策**（对手阵容强度影响升人口紧迫性）；
3. **战术规则**应能反向触发**侦察频率调整**（如濒死状态时提高侦察频率以寻找克制机会）。

建议在 Plan 中增加一个**"数据流图"**章节，明确三个模块的输入输出契约。

---
### 1️⃣ 超几何分布联合概率计算的数学严谨性
#### ✅ 合理之处
- 正确识别了“无放回抽样”场景，选用超几何分布替代二项分布符合自走棋底层机制。
- 将商店多卡槽视为联合事件进行概率推演，方向正确。

#### ⚠️ 关键风险点
| 风险维度 | 问题描述 | 数学/工程影响 |
|:---|:---|:---|
| **行池扣减语义混淆** | “同行卡池扣减”若指棋盘布局行位，则不影响全局牌库；若指卡牌类型/星级分类，需明确映射关系。 | 错误映射会导致 $N$（总牌数）或 $K$（目标牌数）参数漂移，概率失真。 |
| **多槽联合独立性假设** | 多槽刷新并非独立事件，而是**条件依赖的连续抽样**。直接乘积会忽略前序抽取对后序条件的改变。 | 高估稀有卡出现概率，导致决策树偏向激进搜牌。 |
| **降星/重复卡动态池** | 标准超几何分布假设 $K$ 固定，但自走棋存在“重复卡降星”机制，使成功态数量随时间非线性衰减。 | 静态公式无法覆盖中期后期抽卡体验，推演结果与实际偏差 >15%。 |

#### 🔧 修正建议
1. **参数动态化**：维护实时牌库状态 `(N_t, {K_c}_t)`，其中 $K_c$ 为第 $c$ 类卡剩余数量。每次刷新/购买后更新状态。
2. **联合概率严格推导**：采用条件超几何链式法则：
   $$
   P(S_1, S_2, ..., S_m) = \prod_{i=1}^{m} \frac{\binom{K_{target,i}}{k_i} \binom{N_{t+i-1} - K_{target,i}}{slot_i - k_i}}{\binom{N_{t+i-1}}{slot_i}}
   $$
   其中 $N_{t+i-1}$ 为第 $i$ 槽抽取前的剩余牌数。
3. **降星补偿机制**：引入**期望牌数修正因子** $\alpha(c) = 1 + \frac{d_c}{N_t}$（$d_c$ 为已抽取的同卡次数），或直接改用 **Monte Carlo 采样**（单次推演 <0.8ms）处理复杂组合。
4. **验证基线**：对照官方 TFT 概率表（如 3费卡首次出现期望约 6.5 次刷新）进行单元测试，误差容忍度 ≤3%。

### 2️⃣ 7 名对手侦察快照的并发安全与时序更新
#### ✅ 合理之处
- 明确“不可变快照”设计，符合 AI 决策上下文隔离原则。
- 分阶段采集思路契合自走棋回合制节奏。

#### ⚠️ 关键风险点
| 风险维度 | 问题描述 | 并发/内存影响 |
|:---|:---|:---|
| **读写冲突窗口** | 若快照在准备期外被异步线程读取，可能捕获到半更新状态（如装备合成中途）。 | 决策基于脏数据，引发逻辑死锁或越界访问。 |
| **不可变性实现漏洞** | Java/C++ 中仅标记 `final` 不保证深层对象不可变；防御性拷贝缺失会导致引用逃逸。 | 内存泄漏或状态污染，GC 压力骤增。 |
| **时序一致性缺失** | 未定义快照的“逻辑时钟”或检查点（Checkpoint），多线程可能读到不同步的 7 人视图。 | 违反线性一致性（Linearizability），AI 推演失去可比性。 |

#### 🔧 修正建议
1. **强检查点绑定**：仅在 `PreparationPhase.End()` 触发快照生成，禁止运行时中断采集。使用屏障同步（Barrier/Semaphore）确保 7 个快照在同一逻辑帧内冻结。
2. **不可变数据结构**：
   - 使用 `ImmutableMap<OpponentId, OpponentSnapshot>` + 深度克隆（如 Jackson `COPY_NON_NULL` 或 C++ `std::move` 语义）。
   - 内部状态改为值对象（Value Object），禁用可变集合。
3. **无锁读取保障**：主循环通过 `AtomicReference<SnapshotBundle>` 原子替换引用；AI 线程只读。配合 Epoch-Based Reclamation (EBR) 避免 ABA 问题。
4. **并发测试策略**：使用 ThreadSanitizer / JCTools 进行压力测试（1000+ 线程交替读写），验证无数据竞争且快照序列单调递增。

### 3️⃣ 战术建议（利息/升人口/装备合成）的规则决策鲁棒性
#### ✅ 合理之处

#### ⚠️ 关键风险点
| 风险维度 | 问题描述 | 决策质量影响 |
|:---|:---|:---|
| **阈值硬编码** | 利息/升人口阈值未随对局阶段、胜率曲线动态调整。 | 前期保守拖慢节奏，后期僵化错失转型窗口。 |
| **装备合成缺乏优先级图** | 未区分核心件/过渡件/散件，易陷入“囤货不合成”或“盲目合套装”。 | 战力转化率下降 20%~35%，资源浪费。 |
| **不确定性未量化** | 规则未纳入方差惩罚（如升 5 级失败率、刷新空窗期），导致过度优化期望值。 | 实际对局中频繁遭遇“黑天鹅”，AI 表现波动大。 |

#### 🔧 修正建议
1. **效用函数替代硬规则**：将离散规则转为连续评分：
   $$
   U(action) = w_1 \cdot EV_{save} + w_2 \cdot EV_{level} + w_3 \cdot EV_{item} - \lambda \cdot Var(risk)
   $$
   权重 $w_i$ 由当前阶段系数（前期/中期/后期）动态插值。
2. **装备合成决策图**：构建有向无环图（DAG），节点为装备组合，边权为战力增益/金币消耗比。优先遍历核心件子图，散件仅当无路径时启用。
3. **方差感知机制**：引入置信区间调整。例如升人口决策增加项：
   $$
   \Delta U = \beta \cdot \mathbb{I}(WinRate_{last5} < 0.4) \cdot \log\left(\frac{Gold}{LevelCost}\right)
   $$
   低胜率时强制提高升级权重，打破僵局。
4. **退化状态兜底**：明确处理边界（负金、满级、装备锁定、连败转连胜拐点），设置 fallback 策略库（如“保血止损”、“赌命翻盘”模板）。
5. **验证闭环**：使用历史对局回放 + 蒙特卡洛树搜索（MCTS）进行离线回测，对比基准 AI 胜率/经济效率，要求综合指标提升 ≥8%。
